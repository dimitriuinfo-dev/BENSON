- **BENSON 24** (2026-07-08): Waze diagnostic + real root-cause fix. Found via direct adb/manifest inspection (not guesswork): AndroidManifest.xml had zero <queries> entries for individual app packages (Waze/WhatsApp/YouTube/Maps/BlueMail) -- on Android 11+ (targetSdk 36 here), getLaunchIntentForPackage() for one SPECIFIC named package is blocked by package-visibility restrictions unless declared in <queries>, even though the bulk ACTION_MAIN/CATEGORY_LAUNCHER enumeration getInstalledApps() uses for radio/music is exempt from the same restriction -- this is exactly why Magic FM opened but Waze/WhatsApp/YouTube/Maps did not: the fixed-package isPackageInstalled/launchApp path was silently blind to them. Added <queries><package .../></queries> entries for all five. Also confirms the earlier isPackageInstalled/getForegroundPackage diagnostic work was sound -- the underlying check itself was the bug, not the surrounding logic.
- **BENSON 25** (2026-07-09): Fixed 'Waz' STT truncation bug found via live Debug Panel capture: RAW TRANSCRIPT was literally 'open Waz' (English-mode STT, trailing e dropped) -- MENTIONS_WAZE required the whole word 'waze' so it never matched, falling through to a generic OPEN_APP that also couldn't resolve 'Waz' as an app name, producing the false 'Nu gasesc aplicatia Waz pe telefon' loop the user hit repeatedly. Verified via dry-run: 'open Waz'/'Waz'/'open Waze'/'deschide Waze' all resolve to OPEN_WAZE now; full 33-phrase regression suite unaffected.
- **BENSON 26** (2026-07-09): STT handoff race fix: bare wake word (Benson alone, no command in same breath) TTS 'Te ascult' cue finishing wasn't leaving enough buffer before starting the second real STT session -- live testing kept hitting NO_SPEECH_DETECTED right after the cue despite speaking immediately, most likely the audio subsystem hadn't fully released TTS output focus by the instant onFinished fires. Added an explicit 600ms buffer after the TTS callback, before doStartListening() is called, on top of (not instead of) the existing TTS-finished gate. Same-utterance wake+command path (native captures both in one native STT burst, no second session) is unaffected -- this only touches the bare-wake-word branch.
- **BENSON 27** (2026-07-09): Fixed severe CPU/thermal issue found via live device diagnosis: dumpsys cpuinfo showed BENSON at 75-105% CPU continuously with CPU temps up to ~90C once Accessibility Service was actually enabled -- accessibility_service_config.xml was subscribed to typeWindowContentChanged (fires on every UI change, system-wide, in every app, not just BENSON), each event walking up to 400 accessibility nodes and building/sending a JSON payload regardless of whether anything is listening on the JS side. Narrowed to typeWindowStateChanged only, which is all the current getForegroundPackage() consumer (App Launcher launch verification) actually needs -- costs a small fraction as much and only fires on actual foreground app changes. The richer event set can be restored later specifically if/when the screen-snapshot/form-fill feature is wired back into active use, with cost re-measured at that point.
- **BENSON 28** (2026-07-09): Narrowed benson-accessibility's declared capabilities (canRetrieveWindowContent, canPerformGestures both to false; dropped flagRetrieveInteractiveWindows) alongside the earlier event-type narrowing. Live testing showed ColorOS repeatedly auto-disabling the service after the user enabled it in Settings, even after the CPU fix -- read-screen-content plus perform-gestures is a well documented OEM security trigger for sideloaded apps specifically (spyware/screen-scraping heuristic). getForegroundPackage() (the only active consumer right now) only reads event.packageName off the accessibility event object itself, never touches rootInActiveWindow or performs an action, so it needs neither capability. Both are documented to restore only alongside actually wiring the screen-snapshot/click/fillForm/goBack/goHome functions back into active use.
- **BENSON 29** (2026-07-09): Fixed the recurring 'BENSON stops responding to everything' bug, confirmed live twice today (both times right after a command chain hit an unexpected failure). Root cause: handleIncomingText sets loadingRef.current=true at the start and relies on EVERY branch individually resetting it back to false before returning -- but only the routeCommand/Claude tail of the function was ever wrapped in a try/catch. Any unexpected exception thrown earlier (pending-note/pending-mission-task handling, tryStoreFact, the Mission Orchestrator's runMission/governAction chain) would propagate uncaught and skip every one of those inline resets, leaving loadingRef.current stuck true forever -- and since handleIncomingText's very first line is 'if (!msg || loadingRef.current) return', BENSON would silently ignore every subsequent command with no error shown, exactly matching what was observed. Wrapped the entire function body in try/finally so the reset is now guaranteed regardless of which branch runs, throws, or never returns -- existing per-branch resets are left in place (now redundant but harmless) rather than removed, to keep this a minimal, low-risk change.
- **BENSON 30** (2026-07-09): App-launch reliability fix for intermittent 'opens in background, never reaches the screen' failures confirmed live today with WhatsApp and YouTube (both launched -- process started -- but stayed behind BENSON/the launcher instead of coming to the foreground; Waze itself succeeded on some attempts and not others, same underlying flakiness). launchAllowlisted() now calls bringBensonToForeground() (the same mechanism the already-reliable 'revino la Benson' command uses all session) immediately before launchPackage(), with a short 150ms settle delay -- giving the target app's startActivity call a caller that Android's own background-activity-launch exemption rules recognize as having a visible activity, instead of launching from a bare service/background context. Does not change the install-check, verification, or logging steps already in place.
- **BENSON 31** (2026-07-09): Increased the bring-BENSON-to-foreground-then-launch-target gap from 150ms to 450ms after live testing showed YouTube occasionally landing on the home launcher instead of YouTube itself -- likely the two back-to-back startActivity/task-switch transitions colliding on ColorOS's own animation handling when fired too close together. Waze/WhatsApp/Google Maps already worked reliably with the shorter gap; this just gives the first transition more room to settle before the second fires.
- **BENSON 32** (2026-07-09): Deterministic (not timing-guess) fix for the intermittent 'app launched but never reached the visible screen' failures. launchApp() (benson-app-registry) now starts the target app's Activity from appContext.currentActivity (the actual resumed Activity instance) instead of appContext.reactContext (an Application-level context), falling back to reactContext only if no current Activity is available. Android's own background-activity-launch restrictions specifically exempt callers that already have a visible window -- launching from currentActivity is that exemption directly, not a delay gambling that an earlier transition already finished. Replaces guessing at how long to wait after bringBensonToForeground() with removing the need to guess at all for the common case where MainActivity is already resumed. bringToForeground() itself is untouched -- it already worked reliably all session via reactContext and didn't need this change.
- **BENSON 33** (2026-07-09): Real deterministic fixes (Fable 5 review), replacing timing-guess mitigations: (1) App-launcher foreground verification now waits on an actual AccessibilityService TYPE_WINDOW_STATE_CHANGED event (new getForegroundPackage/onForegroundChanged native signal + waitForPackageForeground helper) instead of fixed sleep(450)/sleep(2000) delays -- resolves the instant BENSON/the target app is confirmed foreground, bounded by a 3s timeout that reports unconfirmed rather than guessing success.
